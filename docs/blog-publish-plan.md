## 2. API 사실관계 (검증된 것 / 미확정)

**확인됨**
- 카페 API 호출은 **네이버 로그인(OAuth2) access token 필수**.
- 카페 요청: `clubid`(필수), `menuid`(필수), `subject`(필수), `content`, `image`(선택) 등.

**★ 2026-06-16 curl spike 실측 결과 (`tools/naver_publish_spike.sh`)**
- 토큰 발급(authorization_code 교환) ✅ / 프로필 조회 `/v1/nid/me` ✅ 200 → **OAuth 인증 흐름·토큰 정상**.
- **카페 오픈API에는 게시판/메뉴 목록 조회 API가 없음** — `/v1/cafe/{clubid}/menu/list.json` → **404 "API does not exist"**. 제공 API는 `가입(POST /members)` + `글쓰기(POST /menu/{menuid}/articles)` 둘뿐. → **menuid는 사용자가 게시판 URL에서 수동 확보**해야 함(앱 설계 반영 필요).
- **카페 글쓰기 → 401 `errorCode 024` "Scope Status Invalid"**. 토큰·인증은 정상인데 글쓰기만 차단. 의미: **카페 글쓰기 권한이 활성(검수 완료) 상태가 아니라, 로그인 동의 시 토큰에 해당 scope가 실리지 않음.** = **카페 글쓰기 API는 검수(권한 신청) 완료 전에는 개발자 본인도 사용 불가.**

**미확정 (검수 통과 후 재측정 필요)**
- 카페 글쓰기 성공 응답에 글 URL/`articleid` 포함 여부 (글을 못 올려봐서 미확인).
- `image` 첨부 실제 동작·개수/용량 제약.
- 본문 HTML 허용 태그 범위.

## 3. 핵심 설계: 안드로이드 시스템 공유 → 네이버 카페 앱 (✅ 확정 2026-06-16)

REST 카페 글쓰기 API는 **검수 통과 전 사용 불가**(§2 spike, 401/024). 그래서 **검수가 필요 없는 시스템 공유(ACTION_SEND)** 방식으로 확정.

> **글·이미지 교차 배치 한계(2026-06-17 조사, 같은 날 정정):** 시스템 공유는 (텍스트, 이미지파일들)을 따로 넘기고 **배치는 받는 앱(카페)이 결정** → 본문에 인라인으로 끼워 못 넣음. **→ 시스템 공유 경로에서는 자동 인라인 교차 불가**(우리 채택안 §3 — 그래서 공유 전 정렬 안내 다이얼로그로 처리).
> ~~REST API도 마찬가지~~ **정정:** 카페 API의 **`content`는 HTML이 적용**되므로 `<p>글</p><img src=…><p>글</p>`로 **본문에 인라인 교차 삽입이 가능**하다. 다만 `<img src>`가 가리킬 대상(공개 URL 또는 `image[N]` 업로드 후 반환 URL)과 HTML 허용 범위는 **검수 통과 후 실측 필요**. 즉 인라인이 꼭 필요하면 클립보드 우회가 아니라 **API 경로(검수 전제)**가 정답.

**기기 실측 확인됨(2026-06-16):** 폰에서 사진을 공유 → **네이버 카페 앱 선택 시 카페 선택 + 게시판 선택 + 이미지 첨부 + 글쓰기가 모두 됨.** 사용자가 카페 앱 안에서 최종 "게시"를 누름.

```
[사용자] 메모에서 "카페에 공유"
   │
   ├─ MD 메모 → 읽기 좋은 평문 변환 (제목 + 본문 + 어종/길이/위치 등)
   ├─ 메모의 사진 파일 경로 수집
   │
   └─ share_plus → Share.shareXFiles([사진들], text: 본문, subject: 제목)
            │
            └─ OS 공유 시트 → 사용자가 "네이버 카페" 선택
                    └─ 카페 앱: 카페·게시판 선택 → 내용/사진 채워진 글쓰기 → 사용자가 게시
```

**장점**
- **검수 불필요** — 사용자가 네이버 공식 앱에서 직접 발행(`024` 블로커 우회).
- OAuth·토큰·clubid/menuid 관리 전부 불필요 — 카페/게시판 선택은 카페 앱이 네이티브로 처리.
- 스팸 정책 안전 — 자동 게시가 아니라 사용자가 최종 게시.

**트레이드오프**
- **반자동**: 마지막 "게시"는 카페 앱에서 사용자가 누름(완전 자동 아님). 정책상 오히려 안전.
- 본문은 **평문**으로 들어감(MD 서식 렌더링 안 됨) → 보기 좋은 평문으로 변환해 전달.
- 앱이 **발행 성공/글 URL을 되돌려 받지 못함**(공유는 fire-and-forget).
- **네이버 카페 앱 설치 전제**.

**기기 실측 확인됨(2026-06-16):** 사진 **여러 장** 동시 공유도 카페 앱에서 정상 첨부됨. → 미해결 디테일 없음, 바로 구현 가능.

> 블로그도 동일 패턴 가능성(네이버 블로그 앱 공유). 필요 시 같은 방식으로 추가. 카페가 확인된 1순위.

## 5. ★ 카페 글쓰기 실측 절차 (착수 전 최우선 spike)

목적: **(1) 카페 글쓰기가 앱 소유자 토큰으로 검수 전 동작하는지, (2) 응답에 글 URL/식별자가 오는지**를 코드 작업 전에 확정. 앱 빌드 없이 토큰만 발급해 curl로 확인. 스크립트: `tools/naver_publish_spike.sh`.

**준비**
1. 네이버 개발자센터(developers.naver.com)에서 **애플리케이션 등록**
   - 사용 API: **네이버 로그인 + 카페** (블로그 글쓰기는 목록에 없음=폐지)
   - 환경 추가: **PC 웹**(Callback URL에 `http://localhost` 등록 — spike는 웹 토큰이 빠름)
   - **Client ID / Client Secret** 확보
2. **clubid 확인**: 쓰기 권한 있는 내 카페 PC웹에서 게시판 진입 → 주소/페이지에서 `clubid`(숫자) 확인. `menuid`는 스크립트 [2] 게시판 목록 조회로 획득.
3. **access token 발급** (Authorization Code 흐름)
   - 브라우저로 인증 URL 접속 → 로그인·동의 → redirect의 `code` 확보
     ```
     https://nid.naver.com/oauth2.0/authorize?response_type=code
       &client_id=CLIENT_ID&redirect_uri=http%3A%2F%2Flocalhost&state=spike123
     ```
   - `code`로 토큰 교환
     ```bash
     curl "https://nid.naver.com/oauth2.0/token?grant_type=authorization_code\
&client_id=CLIENT_ID&client_secret=CLIENT_SECRET&code=CODE&state=xyz"
     # → access_token 획득
     ```

**검증 호출** (스크립트가 자동 수행)
4. 게시판 목록 조회로 `menuid` 확인
   ```bash
   curl "https://openapi.naver.com/v1/cafe/CLUBID/menu/list.json" \
     -H "Authorization: Bearer ACCESS_TOKEN"
   ```
5. 카페 글쓰기 1회 호출 후 **응답 전체(raw)** 확인
   ```bash
   curl -X POST "https://openapi.naver.com/v1/cafe/CLUBID/menu/MENUID/articles" \
     -H "Authorization: Bearer ACCESS_TOKEN" \
     --data-urlencode "subject=spike 테스트" \
     --data-urlencode "content=본문 테스트"
   ```
6. **응답에서 확인할 것**
   - [ ] 호출이 **200인가, 권한/검수 오류인가?** → 카페 글쓰기 검수 선행 필요 여부 확정
   - [ ] 글 **URL** 또는 `articleid` 등 식별자 존재? → 발행 후 링크 제공 가능 여부
   - [ ] 한글 인코딩 정상인지(검색에서 깨짐 사례 보고됨 → `--data-urlencode`/UTF-8 확인)
   - [ ] `image` 첨부 동작·개수 제약(후속 호출로 확인)
7. **결과를 이 문서 §2 "미확정"에 반영**하고 설계 확정.

> 주의: 실측은 **본인 테스트 카페/게시판**에 올리고, 스팸 정책에 걸리지 않게 최소 횟수만. 올라간 테스트 글은 확인 후 삭제.

## 6. 리스크 / 미해결

- **★ 최대 블로커 — 카페 글쓰기 검수(확정)**: 2026-06-17 재검증 완료 — 콘솔에서 카페 API 추가·동의항목 설정·callback 정상화 후에도 **서로 다른 토큰 3회 전부 024**. → **검수 승인이 카페 글쓰기의 절대 선행 조건으로 확정.** (024가 단순 설정 누락인 경우도 있으나, 우리 케이스는 설정 후에도 재현되어 검수 게이트로 판명.) 검수는 **출시된 앱 + 명확한 사용 시나리오**가 있어야 통과 가능성↑(인디 앱 반려 위험) → 그래서 정식 릴리스 후 신청하기로 결정(헤더 §4). 신청서 초안: [naver-cafe-검수-신청-초안.md](naver-cafe-검수-신청-초안.md).
- **menuid 수동 확보**: 게시판 목록 API가 없어, 앱에서 대상 게시판을 자동 나열 불가. → 사용자가 **게시판 URL을 붙여넣거나 menuid를 직접 입력**하는 UX 필요.
- **카페 권한**: 임의 대형 카페 자동 배포 불가. "내가 가입·쓰기권한 있는 카페"만.
- **이미지 첨부 실제 제약**: 개수/용량/본문 내 배치 — 검수 후 실측.
- **본문 포맷·응답 URL**: 검수 통과 후 §5 재실행으로 확정.

## 7. 권장 진행 순서 (spike 결과 반영)

1. **먼저 검수 가능성부터 판단** — 카페 글쓰기 검수는 출시 앱·명확한 용도를 요구. 광고/스팸 의심받지 않을 시나리오("사용자가 자기 조행 메모를 자기 카페에 발행")로 신청서 준비.
2. 검수 신청 → 승인되면 같은 토큰으로 §5 글쓰기 spike 재실행 → 응답 URL/이미지 첨부 확정.
3. 그 다음에야 앱 통합(네이버 로그인 SDK + 발행 UX) 착수. **검수 전 코드 작업은 의미 없음.**
